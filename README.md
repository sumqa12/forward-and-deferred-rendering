# forward-and-deferred-rendering

フォワードレンダリングとディファードレンダリングのメリット・デメリットを、ブラウザ上で実際に動かして比較するための WebGL2 描画基盤です。
同じシーンと同じライティング式 (Blinn-Phong + 有限半径の点光源) を 2 つのパイプラインで描画するため、見た目の差やコストの差はパイプラインの違いだけから生まれます。

## 実行方法

ビルド不要です (ES Modules のみ、依存ライブラリなし)。ローカルサーバーで配信してください。

```sh
python3 -m http.server 8000
# → http://localhost:8000/
```

GitHub Pages で公開する場合は、リポジトリのルートをそのまま公開すれば動作します。
WebGL2 と `EXT_color_buffer_float` 拡張が必要です (主要なデスクトップ / モバイルブラウザは対応済み)。

## メリット・デメリット

### フォワードレンダリング

メッシュを描画するたびに、そのメッシュに影響するライトを全部計算して色を確定させる方式。

| メリット | デメリット |
| --- | --- |
| 実装がシンプル。パイプラインが 1 本 | コストが「オブジェクト数 × ライト数」に比例し、ライト増加で急激に重くなる |
| 半透明を自然に扱える (ソートしてブレンド) | 1 パスのライト数に上限があり、超えるとマルチパスでドローコールが増える |
| MSAA がそのまま使える | オーバードローで隠れるピクセルまでライティングしてしまう (Z プリパスで軽減) |
| マテリアルごとに自由なシェーダーを使える | ライトのカリングがオブジェクト単位で粗い |
| G-buffer 不要でメモリ・帯域が少ない | |
| ライトが少ないシーンでは軽い | |

### ディファードレンダリング

G-buffer (アルベド・法線・深度など) に表面情報だけを書き出し、後からスクリーン空間でライティングする方式。

| メリット | デメリット |
| --- | --- |
| コストが「ライトの影響範囲のピクセル数」に比例し、大量ライトに強い | G-buffer のメモリ・帯域が大きい (解像度に比例) |
| 見えているピクセルだけをライティングするのでオーバードローの影響がない | 半透明を扱えない → Forward とのハイブリッドが必要 |
| ライトボリュームで影響範囲だけを計算できる | MSAA が困難 (WebGL2 では実質不可) → FXAA などに頼る |
| G-buffer を SSAO / SSR などに再利用できる | マテリアルの種類が G-buffer のフォーマットに縛られる |
| | ライトが少なくても G-buffer の固定コストがかかる |

## デモで確認できること

右パネルの「シナリオ」ボタンで、各項目を確認しやすい設定に切り替わります。

| シナリオ | 確認できること |
| --- | --- |
| ライト少数・高解像度 | Forward は 1 パスで済む。Deferred は G-buffer の固定コストと大きな RT メモリがかかる |
| 大量の点光源 | ヒートマップで 1 ピクセルあたりのライト計算回数を比較。Forward は追加パスでドローコールが激増 |
| 半透明オブジェクト | Deferred で半透明を G-buffer に書くと不透明に破綻する。ハイブリッドにすると正しく描ける |
| アンチエイリアス | Forward は MSAA が効き、Deferred はジャギーが残る。FXAA で代替できる |
| オーバードロー | Forward では隠れた面の無駄なライティングが発生する。Z プリパスで軽減できる |
| G-buffer の中身 | Deferred が保持するアルベド / 法線 / 深度 / スペキュラを可視化 |

統計パネルには、各方式の CPU 時間 (コマンド発行)、GPU 時間 (パス別、`EXT_disjoint_timer_query_webgl2` が使える環境のみ)、ドローコール数、追加ライトパス数、三角形数、レンダーターゲットのメモリ量を表示します。

## 構成

```
index.html                 UI (パネル、オーバーレイ)
css/style.css
src/
  main.js                  初期化、描画ループ、UI バインディング、統計表示
  core/
    math.js                行列演算
    geometry.js            立方体・球・トーラス・タイル
    mesh.js                VAO / インスタンシング
    gl-utils.js            シェーダー、レンダーターゲット (使用メモリの記録付き)
    gpu-timer.js           GPU 時間計測
  scene/
    scene.js               オブジェクトと点光源 (決定的な乱数で配置)
    camera.js              オービットカメラ
    frame.js               フレームごとの共通データ (ビュー空間のライト、ソート済みオブジェクト)
  renderers/
    shaders.js             GLSL (ライティング式は両方式で共通)
    forward-object-pass.js オブジェクト単位のライトカリング + マルチパス描画 (Forward と Deferred の半透明で共有)
    forward-renderer.js    Z プリパス → 不透明 → 半透明 → MSAA 解決
    deferred-renderer.js   G-buffer → 深度コピー → 全画面の環境光 + ライトボリューム → 半透明 (ハイブリッド)
    light-markers.js       ライト位置の発光球
    post-process.js        トーンマップ、FXAA、ヒートマップ、G-buffer 表示
  ui/scenarios.js          シナリオのプリセット
```

### パイプラインの詳細

**Forward**
1. (任意) Z プリパス: 深度だけを先に描き、以降は `depthFunc(EQUAL)` で見える面だけをシェーディングする
2. 不透明オブジェクトを手前から描画。境界球とライトの影響球の交差判定でライトを絞り込み、1 ドローにつき最大 N 個 (4/8/16/32) まで処理する。超えた分は加算ブレンドの追加パスで描く
3. 半透明オブジェクトを奥から描画 (アルファブレンド + 追加パスは加算)
4. MSAA が有効なら、マルチサンプルのレンダーバッファを `blitFramebuffer` で解決する

**Deferred**
1. G-buffer パス: RT0 `RGBA8` (アルベド + スペキュラ)、RT1 `RGBA16F` (ビュー空間法線 + 光沢度)、深度 `DEPTH_COMPONENT24`。位置は深度から復元する
2. G-buffer の深度をライティング用 FBO にコピーする (サンプリング中のテクスチャはアタッチできないため)
3. 全画面パスで環境光・平行光源・背景を描く
4. 点光源ごとに球メッシュをインスタンシングで 1 ドロー描画し、加算ブレンドする。裏面を `depthFunc(GEQUAL)` で描くことで、カメラがボリューム内にあっても欠けず、影響範囲より奥の面のピクセルシェーダーも起動しない
5. 半透明は Forward のオブジェクトパスで追加描画する (ハイブリッド)
